## 🎯 Purpose and outcome

Create a reviewable, maintainable foundation for FRTB-SA before implementing
market risk calculations. Completion means the repository's files, controls,
contribution workflow, and setup checks are usable and supported by evidence.
It does not mean SBM, DRC, or RRAO has been implemented or validated.

The milestone is named **v0.0.1 - Repo setup**. Its version identifies setup
scope; it does not itself establish a version source, tag, or published release.
Issue #8 defines the consistent release/version convention before tagging.

## 🚪 Entry criteria

- The owner has created the setup milestone and authorized its workstreams.
- Scope describes the intended project and explicitly records unapproved
  platform, regulatory-profile, coverage, and packaging decisions.
- A maintainer can inspect the current repository and its maintenance configuration.
- Every work item has a defined objective, acceptance checklist, dependencies,
  owner, one priority, milestone, and expected evidence.

These are starting conditions, not assertions that all exit criteria pass.

## 🔗 Dependencies and order

Labels and scope inform the remaining setup work. Governance establishes the
active integration branch and contribution procedure. Structure and forms
provide inputs for universal CI. A successful representative CI run supplies
the real check identity needed to finish settings enforcement. Closeout then
verifies all workstreams together. Parallel progress is possible, but a
dependency is not satisfied merely because its issue exists.

All task PRs target `release/v0.0.1` and squash-merge under governance.
Default-branch features such as issue forms and scheduled workflows must be
rechecked after an owner-requested integration into main. Development on the
release branch alone does not prove those features are effective.

## ✅ Exit criteria and evidence

Issue #8 must link evidence that:

- Issues #1–#7 satisfy their full acceptance scope, with merged PRs and
  successful applicable checks; partial work stays visible.
- Existing and new issues and development PRs have the correct owner, one
  priority, and milestone; P1 is confined to confirmed calculation bugs.
- A fresh checkout supports the documented layout, commands, and file
  handling, with usable navigation and no unrelated project-specific paths.
- Effective rulesets, security settings, dependency updates, and review
  coverage match the recorded baseline; pending controls are not called active.
- The universal integrity workflow runs on ordinary PRs to main and the
  active integration branch, detects representative invalid inputs, and has
  its actual check identity attached to the protection rules.
- Forms and policies work from the default branch, and security reporting
  uses a verified private channel.
- Project files consistently identify the MIT license, with its copyright
  and permission notice preserved.
- The release procedure, version convention, adoption/deferment decisions,
  remaining limitations, and next-stage decisions are recorded.

Use commit-bound evidence: identify the PR/commit, commands, results, hosted
run URLs, settings readback date, and any unavailable checks. Static checks
validate repository maintenance; they do not establish runtime or numerical
correctness. Do not fabricate workbook or Excel execution evidence.

## ⏸️ Deferred work and decisions

The engine language/runtime, supported environments, regulatory baseline,
jurisdiction profile, initial instruments/risk classes, and data contracts
remain subject to explicit decisions in [Scope](../SCOPE.md).
A trackable `src/workbook/FRTB_Template.xlsx` path does not establish a
supported workbook or approved Excel engine.

Formula tests, independent benchmark calculations, runtime evidence, and
engine packaging belong to later implementation work. Public Pages, SEO,
social previews, and traffic analytics are outside this setup baseline unless
separately authorized; the repository is already public.

## 📋 Closeout and transition

The owner reviews the issue #8 completion record and any genuine gaps.
Closing this milestone does not merge main, create a tag, publish a release,
or select the next platform or milestone. Those are separate decisions.
When the owner selects the next integration branch, update governance, agent
instructions, and automated PR targets together. Retain protected release
history; do not delete/recreate or force-push the active release branch.
